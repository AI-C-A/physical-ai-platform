# 브라우저 카메라 페어링과 실시간 연결

## Quest처럼 연결 코드로 페어링

1. PC에서 **MLOps → 수집 → 새 수집**으로 세션을 만들고 수집 콘솔의 **장치 → 카메라 연결**을 연다. Quest와 카메라는 각각 연결할 수 있다.
2. **헤드캠 연결** 또는 **전신 카메라 연결**을 누른다. 장치 이름은 용도와 번호로 자동 생성한다.
3. 카메라가 연결된 기기의 브라우저에서 **같은 사이트의 `/collect/camera`**를 연다. PC에 표시된 6자리 카메라 코드를 입력하고 **연결**을 누른다. 링크로 열면 코드가 미리 입력된다.
4. **영상 전송 시작**을 누른다. 장치를 바꾸려면 **사용할 카메라**에서 선택한다. 이때만 카메라 권한을 요청한다. 마이크 권한은 요청하지 않는다. 처음에는 기본 카메라로 권한을 허용한 뒤, 정지하고 장치 목록에서 다른 카메라를 선택할 수도 있다.
5. PC 메인 화면에서 손 추적과 카메라 영상을 확인한다. 미리보기 카드는 손 추적과 같은 헤더에 이름과 수신 상태를 표시하며, 화면 너비에 맞춰 1~4열로 배치된다. 코드는 **장치 → 카메라 연결**에서 발급한다. 연결이 완료되면 창이 닫히고 장치 사이드바에 이름·수신 상태·삭제가 표시된다. 카메라 기기는 페이지를 계속 열어 둔다.

송신 페이지의 **90° 회전**으로 0°·90°·180°·270° 방향을 바꿀 수 있다. 로컬과 PC 미리보기에 함께 반영하며, 원본 영상은 그대로 전송하고 방향만 WebRTC 데이터 채널로 전달한다.

동일 용도에도 여러 카메라를 추가할 수 있다. 예를 들어 `Head 정면`, `Head 측면`, `Full body 정면`을 각각 연결한다. 수집 세션당 최대 16대, gateway 전체 최대 128대이며 실제 동시 수신 성능은 기기·네트워크에 따라 확인해야 한다.

한 기기에 여러 USB 카메라가 연결되어 있으면 송신 페이지의 **카메라 추가 연결**로 별도 연결 칸을 만든다. 각 칸에 서로 다른 코드를 입력하고 카메라를 선택한다. 같은 페이지에서 동일한 물리 카메라를 두 칸이 사용하지 못하게 한다. 라즈베리파이는 브라우저의 카메라 목록에 나타나는 USB/V4L2 장치를 사용할 수 있다. CSI 카메라가 브라우저에 보이지 않으면 아래 MediaMTX 방식이나 OS 쪽 카메라 노출 설정이 필요하다.

### 코드·재연결·정리

- 코드는 5분간 유효하며 한 번만 사용한다. Quest 손 추적 코드와 카메라 코드는 서로 별개다. 용도와 이름은 PC에서 정해지며 송신자가 코드를 입력하면 그대로 표시된다.
- 미연결 상태의 **새 코드 받기**는 이전 코드를 폐기하고 다시 5분을 시작한다. 이미 연결된 송신자는 재발급 요청으로 해제하지 않는다. 장치 사이드바의 **삭제**는 해당 카메라 등록을 삭제한다.
- PC 상세 탭 전환은 연결을 유지한다. PC 새로고침 후에는 gateway가 기억하는 카메라 목록을 읽고 열려 있는 송신자와 다시 연결한다.
- 송신 페이지의 **영상 전송 중지**, 페이지 종료, 권한 해제·장치 분리 시 해당 캡처를 정리한다. PC 미리보기를 정지하면 송신 페이지는 연결 대기로 돌아가며 로컬 카메라 미리보기는 계속할 수 있다.
- 송신 페이지를 새로고침하면 PC에서 새 코드를 발급해야 한다. 토큰을 브라우저 저장소에 보관하지 않는다. gateway 재시작 또는 1시간 이상 카메라 API 활동이 없으면 카메라를 다시 추가한다. 이 임시 카메라 연결 정보는 디스크에 저장하지 않는다.
- 수집이 종료·삭제되면 카메라 권한도 더 이상 사용할 수 없다. 종료 감지는 다음 신호 조회 때 반영된다.

### 네트워크

송신 기기는 신뢰할 수 있는 **HTTPS** 사이트로 접속해야 한다. 개발 PC의 localhost는 예외지만 다른 기기에서 접근하는 일반 HTTP LAN 주소는 카메라 권한 조건을 충족하지 않는다.

`/api/quest/cameras/*`는 기존 Quest gateway로 프록시한다. 서버는 코드와 WebRTC 연결 정보만 교환하고, 영상은 브라우저 간 WebRTC로 전송한다. 신호 조회 간격 약 700ms는 연결 제어용이며 영상 프레임 전송 주기가 아니다.

기본 설정은 같은 LAN에서 접근 가능한 ICE 후보를 사용한다. 다른 네트워크·격리된 Wi-Fi에서는 STUN/TURN이 필요할 수 있다. gateway 환경 변수 `CAMERA_ICE_SERVERS`에 표준 `RTCIceServer[]` JSON을 지정할 수 있다. TURN URL·username·credential은 운영하는 서비스에서 발급받아 넣는다. 이 설정은 연결된 브라우저에 전달되므로 단기 자격증명을 사용한다. HTTPS 터널만으로 미디어 NAT 통과까지 해결되지는 않는다.

현재 기존 Quest 수집 API와 같은 신뢰 경계를 사용한다. 인터넷에 gateway를 노출할 때는 기존 수집 API를 포함해 인증된 서비스 접근 경계를 마련해야 한다.

### 자동 검증

```sh
node --test gateway/camera-relay.test.mjs
npm run test:unit -- src/pages/collect/camera
npm run verify:cameras
```

브라우저 검증은 임시 gateway와 frontend를 사용한다. Chrome 테스트 캡처만 사용하고 실제 카메라를 켜지 않는다. **Head 2대 + Full body 1대 → 실제 WebRTC 프레임 수신 → 상세 탭 전환 → PC 새로고침 → 한 대 제거 → 코드 갱신 → 재연결 → 캡처 정리**를 검증한다. 결과와 스크린샷은 `artifacts/browser-cameras-<timestamp>/`에 남는다. 실기기 권한·지연·화질은 별도 검증 대상이다.

## 외부 WebRTC 주소로 연결

수집 콘솔의 **수집 → 시연 카메라**에서 헤드캠과 전신 카메라를 각각 연결한다. 두 영상은 독립적인 WebRTC 연결을 사용한다. 실제 영상 재생이 시작되어야 `영상 수신 중`으로 표시한다. 다른 상세 탭을 열어도 연결은 유지되고, 콘솔을 떠나거나 연결 해제를 누르면 종료한다.

실제 수집 모드에서는 녹화 시작 시 연결된 카메라의 수신 영상을 에피소드별로 저장한다. 외부 주소는 현재 화면에서만 유지한다. 카메라 영상과 관절 좌표는 같은 에피소드에 속하지만, 하드웨어 시계 동기화나 프레임 단위 정렬을 보장하지 않는다. 전신 영상 연결은 전신 관절 추적을 의미하지 않는다. 실제 하드웨어로 지연을 측정하기 전에는 지연 수치를 보장하지 않는다.

## 라즈베리파이 송출

권장 구성: Raspberry Pi 카메라 → Pi의 MediaMTX → 같은 LAN의 PC 브라우저.

MediaMTX 설치 후 `mediamtx.yml`의 `paths`에 아래를 설정한다. 카메라 1대에 Pi 1대를 사용하는 경우 각 Pi에는 자기 카메라 경로만 설정하고 `rpiCameraCamID: 0`을 사용한다. 두 카메라를 한 Pi에 연결했다면 실제 카메라 번호를 확인한다.

```yaml
paths:
  head:
    source: rpiCamera
    rpiCameraCamID: 0
    rpiCameraWidth: 1280
    rpiCameraHeight: 720
    rpiCameraFPS: 30
  body:
    source: rpiCamera
    rpiCameraCamID: 1
    rpiCameraWidth: 1280
    rpiCameraHeight: 720
    rpiCameraFPS: 30
```

이는 초기 측정을 위한 해상도/FPS이며 성능 보장이 아니다. USB 카메라는 `rpiCamera` 대신 해당 장치에 맞는 FFmpeg/GStreamer 송출 구성이 필요하다.

## 브라우저 연결

1. MediaMTX 기본 구성에서는 `http://<Pi IP>:8889/head`를 열어 영상 송출을 먼저 확인한다.
2. 수집 콘솔의 헤드캠 주소에 `http://<Pi IP>:8889/head/whep`, 전신 카메라 주소에 `http://<Pi IP>:8889/body/whep`를 입력한다.
3. 각각 **카메라 연결**을 누른다. PC가 HTTPS 사이트를 사용하면 카메라 WHEP 주소도 신뢰하는 인증서가 있는 HTTPS로 제공해야 한다.
4. 연결 오류 시 주소, 서버 접근 권한, CORS와 미디어 포트의 네트워크 접근을 확인하고 **다시 연결**한다.

현재 수신기는 같은 LAN에서 접근 가능한 WHEP 서버용이다. 브라우저의 전체 ICE 후보를 모아 POST하며, TURN 인증이나 외부망 NAT 통과 설정은 제공하지 않는다. MediaMTX의 `webrtcAdditionalHosts`에는 PC에서 접근 가능한 Pi 주소를 설정하고 미디어 UDP 포트(기본 8189)를 허용한다. HTTPS 프록시만 연결해도 미디어 포트가 차단되어 있으면 영상이 나오지 않는다.

다른 origin의 서버는 콘솔 origin에 대한 CORS를 허용하고 `Location` 응답 헤더를 노출해야 한다. WHEP 서버는 SDP POST에 `201`과 세션 `Location`을 반환하고, 연결 해제 시 해당 URL의 DELETE를 지원해야 한다. 세션 URL은 WHEP 주소와 같은 origin이어야 한다. 프록시는 POST/DELETE 및 Location 헤더를 유지해야 한다. 계정 정보를 URL에 넣는 연결은 지원하지 않는다.

## 지연과 동기화 검증

- 카메라에 밀리초 타이머나 LED를 보여주고 원본과 PC 화면을 함께 촬영해 촬영부터 화면 표시까지 지연의 p50/p95를 측정한다. 네트워크 RTT를 전체 영상 지연으로 사용하지 않는다.
- 헤드캠·전신 카메라를 동시에 켠 상태에서 유선/무선, 해상도/FPS별로 비교한다. 연결 해제, 재연결, 상세 탭 전환과 콘솔 종료도 확인한다.
- 학습 데이터 저장으로 확장할 때는 각 장치의 촬영 타임스탬프, 공통 시간 기준과 시계 오차, Episode 시작·정지 ACK, 원본 전송 완료를 함께 기록해야 한다. 브라우저 도착 시간만으로 Quest와 프레임을 맞추지 않는다.

공식 참고:

- [MediaMTX Raspberry Pi 카메라](https://mediamtx.org/docs/publish/raspberry-pi-cameras)
- [MediaMTX WebRTC/WHEP](https://mediamtx.org/docs/read/webrtc)
- [MediaMTX WebRTC 연결과 코덱](https://mediamtx.org/docs/features/webrtc-specific-features)

카메라 종류의 연결 버튼을 누르면 새 연결 코드를 발급하며 서버 발급 시점부터 5분 동안 유효하다. 만료 시 코드를 숨기고 **새 코드 받기**를 표시한다. 시간 경과나 탭 복귀만으로 코드를 자동 갱신하지 않는다. Quest와 카메라는 같은 코드 화면을 사용한다.

## 원본과 별도의 분석 카드

각 카메라 옆에 역할에 맞는 분석 카드를 표시한다. 전신은 **4D Humans 3D 메시**, 헤드는 **세그멘테이션 + 손 관절**을 표시한다. 분석 카드의 정지/시작은 원본 영상 연결에 영향을 주지 않는다. CUDA 데스크탑 서버 설정은 [카메라 분석 서버 안내](../perception/README.md)를 따른다.

## 연결 UI와 mock 검증

새 수집 세션은 장치 패널을 기본으로 표시한다. 카메라 코드 발급만으로 영상이나 분석 조작을 표시하지 않는다. 연결 완료 후 사이드바에 장치가 나타나고, 영상 수신 후 분석 카드를 표시한다.

`VITE_COLLECTOR_ORIGIN`에 기기에서 접근 가능한 HTTPS origin을 지정하면 실제 모드의 연결 안내에 전체 주소를 사용한다. mock은 현재 origin을 사용한다.

mock의 새 수집 세션도 같은 카메라 UI와 WebRTC peer를 사용한다. 서버 역할은 동일 origin의 localStorage와 Web Locks로 대체하므로 같은 브라우저의 탭 사이에서 시험한다. 별도 기기 연결은 실제 모드에서 검증한다. 예전 Human Demonstration profile의 세션은 기존 소스 구성을 보존한다.

`node scripts/verify-mock-camera.mjs`는 가상 카메라로 코드 발급, 페어링, 사이드바 표시, 영상 수신, 새로고침 재연결을 검증한다.

## 에피소드 저장과 조회

- `npm run gateway:quest`와 `npm run dev:collection`를 실행하면 관제는 Mock, 수집은 실제 HTTP 저장소를 사용한다. 전체 Real 모드는 `npm run dev:real`, 순수 시연은 `npm run dev:mock`이다. 배포용 혼합 빌드는 `npm run build:collection`이며 `/api/quest`를 gateway로 프록시해야 한다.
- Quest에서 손 추적을 시작하고 PC에 카메라 영상이 표시되면 **Episode 녹화 시작 → Episode 녹화 정지 → 녹화본 저장** 순서로 수집한다. 녹화를 시작한 뒤 추가한 카메라는 다음 에피소드부터 포함된다.
- 손 관절·머리 위치는 NDJSON, 카메라별 영상은 WebM(지원하지 않으면 MP4), 세션·에피소드 메타데이터는 JSON으로 `data/quest`에 남는다. `QUEST_COLLECTION_DATA_DIR`로 저장 경로를 지정할 수 있다.
- 카메라는 PC가 수신한 영상을 MediaRecorder로 기록한다. 녹화·전송이 끝날 때까지 PC 수집 페이지와 장치 송신 페이지를 유지한다. 영상은 1초 단위 조각을 순서대로 전송하며 중복 재전송은 제거한다. PC 대기 큐 32MB, 조각 8MB, 영상당 512MB, 손 데이터 에피소드당 64MB를 초과하면 완료로 처리하지 않는다.
- 손 추적 종료 응답과 모든 영상 전송을 확인한 에피소드만 저장할 수 있다. 페이지 이탈·연결 끊김으로 영상이 미완료된 경우 폐기 후 새 에피소드로 수집한다. 원본을 받지 못한 녹화를 성공으로 표시하지 않는다.
- **MLOps → 수집 에피소드**에서 세션 종료 전에도 목록·저장 상태·재생·원본 다운로드를 확인한다. 저장된 에피소드는 데이터 카탈로그에서도 바로 확인할 수 있다.
- `node scripts/verify-quest-collection.mjs`는 모사 WebXR과 Chrome 테스트 카메라 2대로 실제 gateway 저장·페이지 새로고침·영상 재생·Range 다운로드를 검증한다. 실제 Quest/Pi의 성능·연결 검증은 별도로 수행해야 한다.
